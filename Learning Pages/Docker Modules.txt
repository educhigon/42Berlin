● Module 1 — What is a container, and why does it exist?
####################################
####################################

  The problem Docker solves

  You've built Webserv. Imagine you want to run it on another machine. What do you need?

  - The right OS version
  - The right compiler / libraries
  - The right config files in the right paths
  - The right user permissions
  - Maybe a specific version of OpenSSL

  If anything is off, it breaks. The classic developer complaint: "It works on my machine."

  Before Docker, the solution was Virtual Machines (VMs). A VM emulates an entire computer — CPU, RAM, disk, its own OS kernel. It works, but it's heavy:

  Your physical machine
  └── Hypervisor (VMware, VirtualBox...)
      ├── VM 1: full Linux OS (1GB RAM, 10GB disk) → runs your app
      ├── VM 2: full Linux OS (1GB RAM, 10GB disk) → runs another app
      └── VM 3: full Linux OS (1GB RAM, 10GB disk) → runs another app

  Each VM boots a whole OS. Slow to start, wastes resources.

  ---
  The container idea

  A container takes a different approach. Instead of virtualizing the hardware, it shares the host OS kernel but isolates everything else — filesystem,
  processes, network, users.

  Your physical machine
  └── Linux kernel (shared)
      ├── Container 1: isolated filesystem + processes → runs NGINX
      ├── Container 2: isolated filesystem + processes → runs WordPress
      └── Container 3: isolated filesystem + processes → runs MariaDB

  Each container thinks it's alone on the machine. It has its own filesystem, its own process list (starts at PID 1), its own network interface. But it's
  not running a separate kernel — it's using yours.

  Result: Containers start in milliseconds, use megabytes instead of gigabytes, and you can run dozens on a laptop.

  ---
  The key insight: a container is just a process

  This is what most people miss at first.

  A container is not a mini-VM. It's a regular Linux process with extra restrictions applied by the kernel:

  - Namespaces — what the process can see (its own PID table, its own network, its own filesystem view)
  - Cgroups — what the process can use (CPU limits, memory limits)

  That's it. When you run a container with NGINX inside, the host kernel is running an NGINX process — it just can't see the rest of your system.

  You can verify this: if you run a Docker container on Linux and then do ps aux on the host, you'll see the container's process right there in the list.

  ---
  Why this matters for your project

  Your Inception project has three containers:

  ┌───────────┬───────────────────────────┬───────────────────────────────────────────────────┐
  │ Container │       What it runs        │                   Why isolated                    │
  ├───────────┼───────────────────────────┼───────────────────────────────────────────────────┤
  │ NGINX     │ Web server, handles HTTPS │ Exposed to internet, should not touch DB directly │
  ├───────────┼───────────────────────────┼───────────────────────────────────────────────────┤
  │ WordPress │ PHP application           │ Needs its own PHP config, talks to DB privately   │
  ├───────────┼───────────────────────────┼───────────────────────────────────────────────────┤
  │ MariaDB   │ Database                  │ Should never be reachable from outside            │
  └───────────┴───────────────────────────┴───────────────────────────────────────────────────┘

  If any one of them crashes or gets compromised, the others keep running. If WordPress needs PHP 8.1 and something else on your system uses PHP 7, no
  conflict — each container has its own.

  ---
  One more thing: images vs containers

  This trips everyone up at the start.

  - An image is a blueprint — a read-only snapshot of a filesystem + metadata (like a class definition in C++)
  - A container is a running instance of that image (like an object created from that class)

  You can run 10 containers from the same image. Each gets its own writable layer on top, so they don't interfere.

  MariaDB image (read-only blueprint)
  ├── Container A (running) — has its own data on top
  └── Container B (running) — has its own data on top

  ---
  That's Module 1. The TL;DR:

  ▎ A container is an isolated Linux process. It shares your kernel but has its own view of the filesystem, network, and processes. Images are blueprints;
  containers are running instances.

● Module 2 — Docker Images and Layers
####################################
####################################

  What is an image?

  An image is a read-only filesystem snapshot plus some metadata (what command to run, what port to expose, etc.).

  Think of it like a tar archive of a minimal Linux filesystem — /bin, /etc, /usr, etc. — frozen in time. When you start a container from it, Docker unpacks
   that filesystem and runs your process inside it.

  The layer system

  Here's where it gets interesting. Images are not monolithic blobs. They're built in layers, stacked on top of each other.

  Each instruction in a Dockerfile creates one layer:

  Layer 4: COPY my-config.conf /etc/nginx/   ← your config file
  Layer 3: RUN apt-get install -y nginx       ← nginx binary + deps added
  Layer 2: RUN apt-get update                 ← package list added
  Layer 1: FROM debian:bookworm-slim          ← base debian filesystem

  Each layer only stores the diff from the layer below it. Layer 3 doesn't re-store the entire filesystem — just the files that apt-get install nginx added
  or changed.

  Why layers matter: caching

  This is the practical payoff. When you rebuild an image, Docker checks each layer:

  ▎ "Did anything change since I last built this? If not, reuse the cached layer."

  So if you change your config file (Layer 4), Docker reuses layers 1-3 from cache and only rebuilds layer 4. Fast.

  But if you change Layer 2, Docker invalidates all layers above it — layers 3 and 4 get rebuilt too.

  This has a direct consequence for how you write Dockerfiles:

  # BAD — changes to your app code invalidate the apt-get cache
  FROM debian:bookworm-slim
  COPY my-app-code/ /app/        ← if this changes, next line runs again
  RUN apt-get install -y nginx   ← slow, reinstalls every time

  # GOOD — stable things first, changing things last
  FROM debian:bookworm-slim
  RUN apt-get install -y nginx   ← cached after first build
  COPY my-app-code/ /app/        ← only this layer rebuilds on code changes

  The writable layer on top

  When a container starts, Docker adds one writable layer on top of the read-only image layers. All writes the container makes go there.

  [writable layer]     ← container writes here (deleted when container stops)
  ─────────────────
  [Layer 4] read-only
  [Layer 3] read-only
  [Layer 2] read-only
  [Layer 1] read-only

  This is why:
  - The image never gets modified by running containers
  - Two containers from the same image don't share writes
  - When a container stops, its writes are gone — unless you use a volume (that's Module 5)

  Image naming

  Images are identified as name:tag. The tag is the version:

  debian:bookworm-slim
  nginx:1.25
  mariadb:11.2

  Your project forbids the latest tag — because latest is ambiguous. It just means "whatever was most recently pushed," and that changes. Using explicit
  versions makes your build reproducible.

  ---
  That's Module 2. Key things to retain:

  - An image is a stacked set of read-only filesystem layers
  - Each Dockerfile instruction = one layer
  - Layers are cached — order matters for build speed
  - Running containers add a writable layer on top, which is temporary
  - Tags identify versions — latest is a bad default

  One question before Module 3: given that the writable container layer is temporary, what do you think would happen to your WordPress database if the
  MariaDB container crashed and restarted?

● Great questions — let me address each one.

  ---
  "Overhead" clarification

  In computing, overhead means extra work the system has to do that isn't directly your program running — it's the cost of the infrastructure around it.

  A VM has overhead because when your program inside the VM says "write to disk" or "open a network socket," the hypervisor has to intercept that call,
  translate it, and pass it to the real hardware. Extra steps every time.

  A container has almost none because when your program says "write to disk," the kernel just... does it. There's no interception. The fences
  (namespaces/cgroups) are checked at setup time, not on every operation.

  Analogy: VM is like having a translator in every conversation. Container is like learning the language yourself — same conversation, no middleman.

  ---
  Your fence analogy — it's good, but one correction

  ▎ "each Dockerfile refers to a specific layer"

  The relationship is actually the reverse:

  - One Dockerfile describes one image
  - Each line in that Dockerfile creates one layer
  - One image runs as one container

  So your fence analogy is right, but the fence IS the Dockerfile. Each plank you add (each line) is a layer. The finished fence is the image. The thing
  standing in your garden is the container.

  Dockerfile (instructions to build a fence)
    Line 1: FROM debian  →  Layer 1 (the posts)
    Line 2: RUN apt install nginx  →  Layer 2 (the planks)
    Line 3: COPY config  →  Layer 3 (the paint)
          ↓
      Image (the finished fence blueprint)
          ↓
      Container (the fence actually standing in your garden)

  ---
  "How do you define what goes in each Dockerfile?"

  One Dockerfile = one service = one container. You don't split one service across multiple Dockerfiles.

  For your project:
  - nginx/Dockerfile — builds the NGINX image
  - wordpress/Dockerfile — builds the WordPress+php-fpm image
  - mariadb/Dockerfile — builds the MariaDB image

  Within each Dockerfile, you order lines by stability — least-changing things first so cache is preserved. But you're not choosing what to separate based
  on update rate — that's already decided: one service, one Dockerfile.

  ---
  Stack analogy for the writable layer

  Yes, that's a decent analogy. Temporary, scoped to the lifetime of the container, gone when it stops.

  But the heap/stack confusion comes from thinking containers share memory — they don't at all. Each container has its own completely separate filesystem
  and memory space. They're not like two functions in the same program.

  ---
  The two databases question — this is the most important one

  ▎ "I don't quite get how we have two databases running at the same time"

  You don't. There's only one database: MariaDB, running in its own container.

  What you have is:
  - MariaDB container — the database engine, stores all the data on disk (via a volume)
  - WordPress container — the PHP application, reads/writes data by talking to MariaDB over the network

  WordPress doesn't store data itself. It connects to MariaDB like a client connects to a server. Same as how your Webserv project didn't store the files —
  it just served them from disk.

  Now, your question about what happens when MariaDB crashes:

  - The MariaDB container crashes and restarts
  - Its data is safe — because it lives in a volume (persistent disk storage), not in the writable container layer
  - WordPress will get database connection errors until MariaDB comes back up
  - Once MariaDB restarts, WordPress reconnects and everything works again

  This is exactly why volumes exist — and why we'll cover them properly in Module 5.

  Quick answer before we move on:

  ---
  Memory and containers

  Yes, you're right. A container does allocate real memory. The fence analogy covers visibility and access control but not resource usage.

  More complete mental model:

  - Fence = what the process can see and access (namespaces)
  - Budget = how much CPU/memory it can use (cgroups)

  When a container runs, the process inside uses real RAM from your host, just like any other process. If you run 3 containers, you have 3 processes
  consuming memory. The kernel tracks which memory belongs to which process normally — containers don't change that.

  What "its own memory" means is simpler than it sounds: one process can't read another process's memory. That's not a Docker thing — that's just how Linux
  processes work. Docker doesn't add anything special there.

  So the fence isn't just about access — it's also about:
  1. What you can see (filesystem, network, other processes)
  2. What you can use (CPU, RAM limits if configured)
  3. What you can affect (can't write to other containers' filesystems)

  But the underlying RAM is still your host's RAM. No magic duplication.

● Module 3 — Writing a Dockerfile
####################################
####################################

  A Dockerfile is a plain text file named exactly Dockerfile (no extension). It's a list of instructions that Docker executes top to bottom to build an
  image.

  The essential instructions

  FROM — the base image to start from

  FROM debian:bookworm-slim

  Every Dockerfile starts with this. You're saying: "start with this existing filesystem snapshot, then add my stuff on top." For your project, you'll use
  debian:bookworm-slim or alpine:3.19 — minimal Linux systems.

  ---
  RUN — execute a shell command during the build

  RUN apt-get update && apt-get install -y nginx

  This runs during docker build, not when the container starts. The result (the installed files) becomes a new layer. You'll use this to install software.

  Note the && chaining — this is intentional. If you write:

  RUN apt-get update
  RUN apt-get install -y nginx

  That's two layers. The apt-get update layer gets cached separately, and later when you add more packages, Docker might use a stale package list from
  cache. One RUN with && = one layer, always fresh together.

  ---
  COPY — copy files from your machine into the image

  COPY conf/nginx.conf /etc/nginx/nginx.conf

  Source is relative to where your Dockerfile is. Destination is inside the image filesystem.

  ---
  EXPOSE — document which port the container listens on

  EXPOSE 443

  This doesn't actually open anything — it's documentation. The actual port mapping happens when you run the container. But it's good practice and
  docker-compose uses it.

  ---
  CMD — the command to run when the container starts

  CMD ["nginx", "-g", "daemon off;"]

  This is what actually launches your service. Notice the array format ["executable", "arg1", "arg2"] — this is important and connects directly to the PID 1
   topic in Module 9. For now, just use this format.

  ---
  ENV — set environment variables inside the container

  ENV NGINX_VERSION=1.25

  ---
  ARG — build-time variables (not available at runtime)

  ARG DB_PASSWORD

  We'll cover the difference between ARG and ENV in Module 8.

  ---
  A real example: minimal NGINX container

  FROM debian:bookworm-slim

  RUN apt-get update && apt-get install -y \
      nginx \
      && rm -rf /var/lib/apt/lists/*

  COPY conf/nginx.conf /etc/nginx/nginx.conf

  EXPOSE 443

  CMD ["nginx", "-g", "daemon off;"]

  Line by line:
  1. Start from minimal Debian
  2. Update package list, install nginx, then delete the package cache (smaller image)
  3. Copy your custom nginx config into the image
  4. Document that port 443 will be used
  5. When container starts, run nginx in the foreground

  ---
  Building and running it

  # Build the image, tag it "my-nginx"
  docker build -t my-nginx .

  # Run it, mapping host port 8080 to container port 443
  docker run -p 8080:443 my-nginx

  The . in docker build means "look for a Dockerfile in the current directory."

  ---
  The filesystem inside the container

  When this container runs, it has a complete Linux filesystem:

  /bin, /etc, /usr, /var ...   ← came from debian:bookworm-slim
  /etc/nginx/nginx.conf        ← your COPY instruction
  /usr/sbin/nginx              ← installed by apt-get

  The process running inside thinks it's on a full Debian system. It has no idea it's a container.

  ---
  Two things to notice that connect back to your project:

  1. daemon off; in the CMD — nginx by default starts and then puts itself in the background (daemonizes). In a container that kills it, because the
  foreground process exits and Docker thinks the container is done. daemon off; keeps it in the foreground. This is the beginning of the PID 1 story.
  2. rm -rf /var/lib/apt/lists/* — after installing packages you delete the apt cache. It's not needed at runtime and just makes the image bigger. This kind
   of housekeeping is standard practice.

  What questions do you have before Module 4? Specifically: does the relationship between docker build (creates image) and docker run (creates container
  from image) make sense?

  5) The daemon thing — this needs a proper explanation

  What is a daemon?

  A daemon is a program that runs in the background as a system service. On Linux, most servers (nginx, sshd, mysqld) are daemons. When you start them
  normally, they do this:

  1. Process starts (PID 1234)
  2. Process forks a child (PID 1235)
  3. Parent (PID 1234) exits
  4. Child (PID 1235) keeps running in the background

  The terminal gets control back immediately. The service is running "behind the scenes."

  This is normal and useful on a real server — you start nginx, get your shell back, do other things.

  Why this kills a container

  Docker watches the process you told it to run. When that process exits, Docker considers the container done and stops it.

  docker run nginx
  → starts nginx (PID 1)
  → nginx forks a child, then exits  ← Docker sees PID 1 exit
  → Docker stops the container       ← child is also killed

  The service barely started before the container shut down.

  daemon off; tells nginx: skip the fork, stay in the foreground, be PID 1 yourself. Docker watches it, it never exits, container keeps running.

  Every service you run in a container needs this treatment — run in the foreground, don't daemonize.

  ---
  The apt cache — you want to flush it

  The cache (/var/lib/apt/lists/) is the downloaded package index — lists of what packages exist and where to download them from. It's used by apt-get
  install to find packages.

  After apt-get install finishes, the cache is useless. The packages are already installed. But it takes up space — sometimes 50-100MB.

  Since images are distributed and stored, smaller = better. You delete it because:
  - You already used it (packages are installed)
  - You'll never need it again inside this container
  - Keeping it just bloats the image for no reason

  This is different from Docker's layer cache (which lives on your host machine and speeds up builds). The apt cache lives inside the image itself.

  This is where things get tangible. Let's go through the key docker run options you'll actually use.

  ---
  Basic run

  docker run nginx:1.25

  Starts a container from the nginx:1.25 image. Runs in the foreground — you see its output, Ctrl+C stops it.

  ---
  Detached mode (-d)

  docker run -d nginx:1.25

  docker logs <id>   # see its output

  Port mapping (-p)

  Remember: containers have their own network namespace — their own IP, their own ports. Port 80 inside a container is NOT your host's port 80.

  docker run -p 8080:80 nginx:1.25

  Format: -p host_port:container_port

  This says: "forward traffic from my machine's port 8080 into the container's port 80."

  Browser → localhost:8080 → host → container:80 → nginx

  For your project, NGINX listens on port 443 inside its container, and you map it to port 443 on the host. That's the only port exposed to the outside
  world.

  ---
  Environment variables (-e)

  docker run -e DB_PASSWORD=secret -e DB_USER=admin mariadb:11.2

  hardcoding it in the image.

  docker run --name my-database mariadb:11.2

  more on that in Module 6.

  docker run -it debian:bookworm-slim bash

  docker run --restart unless-stopped nginx:1.25

  ┌────────────────┬────────────────────────────────────────────┐
  │     Policy     │                  Behavior                  │
  ├────────────────┼────────────────────────────────────────────┤
  │ no             │ Never restart (default)                    │
  ├────────────────┼────────────────────────────────────────────┤

  ├────────────────┼────────────────────────────────────────────┤
  │ always         │ Always restart, even on clean stop         │
  ├────────────────┼────────────────────────────────────────────┤
  │ unless-stopped │ Restart unless you manually stopped it     │
  └────────────────┴────────────────────────────────────────────┘

  ---
  Volumes (-v) — preview

  Format: -v host_path:container_path

● Module 5 — Volumes
####################################
####################################

  Remember the writable layer from Module 2? When a container stops or crashes, that layer is gone. For stateless services (like NGINX serving static files)
   that's fine. For a database, it's a disaster — you'd lose all your data every restart.

  Volumes solve this.

  ---
  What a volume is

  A volume is a directory that lives outside the container's filesystem, on your host machine's real disk. You mount it into the container at a specific
  path. The container reads and writes it like a normal directory — but the data actually lives on the host.

  Host disk: /home/gonzalo/data/db/   ←── real files here, survive forever
                      ↕ mounted
  Container: /var/lib/mysql/          ←── MariaDB writes here

  When the container restarts, the data is still there. When you delete the container entirely and recreate it, the data is still there.

  ---
  Two types of volumes

  Bind mount — you specify the exact host path:
  volumes:
    - /home/gonzalo/data/db:/var/lib/mysql
  host_path:container_path. You control where it lives. Your project requires this — data must be at /home/login/data.

  Named volume — Docker manages the location:
  volumes:
    - db-data:/var/lib/mysql
  Docker stores it somewhere under /var/lib/docker/volumes/. You refer to it by name, not path. Easier but less control.

  Your project uses bind mounts because the subject specifies the exact host path.

  ---
  Why each service in your project needs volumes

  MariaDB — stores the actual database files. Without a volume, every restart wipes your WordPress content, users, settings. Everything.

  WordPress — stores uploaded media, themes, plugins. Without a volume, any file a user uploads disappears on restart.

  NGINX — stateless. Serves requests, doesn't store anything. No volume needed.

  ---
  Volumes in docker-compose

  services:
    mariadb:
      volumes:
        - /home/gonzalo/data/db:/var/lib/mysql

    wordpress:
      volumes:
        - /home/gonzalo/data/wordpress:/var/www/html

  That's it. Docker-compose handles the mounting when it starts the containers.

  ---
  One important gotcha

  The host directory must exist before the container starts, or Docker creates it as root — which can cause permission problems. You'll handle this in your
  Makefile:

  mkdir -p /home/gonzalo/data/db
  mkdir -p /home/gonzalo/data/wordpress

  ---
  Volumes vs the writable container layer — summary

  ┌───────────────────────────┬──────────────────┬────────────────────────────┐
  │                           │  Writable layer  │           Volume           │
  ├───────────────────────────┼──────────────────┼────────────────────────────┤
  │ Lives                     │ Inside container │ On host disk               │
  ├───────────────────────────┼──────────────────┼────────────────────────────┤
  │ Survives container stop   │ No               │ Yes                        │
  ├───────────────────────────┼──────────────────┼────────────────────────────┤
  │ Survives container delete │ No               │ Yes                        │
  ├───────────────────────────┼──────────────────┼────────────────────────────┤
  │ Shared between containers │ No               │ Yes (if mounted in both)   │
  ├───────────────────────────┼──────────────────┼────────────────────────────┤
  │ Use for                   │ Temp files, logs │ Any data that must persist │
  └───────────────────────────┴──────────────────┴────────────────────────────┘

  That last row — shared between containers — is worth noting. You could theoretically mount the same host directory into two containers. Your project
  doesn't need this, but it's possible.

● Module 6 — Networking Between Containers
####################################
####################################

  You have three containers. They need to talk to each other:

  NGINX → WordPress (to forward PHP requests)
  WordPress → MariaDB (to query the database)

  But containers are isolated — they each have their own network namespace. How do they reach each other?

  ---
  Docker networks

  A Docker network is a private virtual network that containers can join. Containers on the same network can reach each other. Containers on different
  networks cannot.

  [ inception network ]
      ├── nginx       (IP: 172.18.0.2)
      ├── wordpress   (IP: 172.18.0.3)
      └── mariadb     (IP: 172.18.0.4)

  Docker assigns each container an IP on that network. But you never use IPs directly — they can change. Instead, Docker provides automatic DNS resolution
  by container name.

  ---
  DNS by container name

  Inside the inception network, containers can reach each other by name:

  nginx can ping "wordpress"
  wordpress can ping "mariadb"

  So in your WordPress config, the database host isn't 172.18.0.4 — it's just mariadb. Docker resolves it automatically.

  This is why naming your containers matters (container_name: mariadb in docker-compose). The name becomes the hostname on the network.

  ---
  Defining the network in docker-compose

  services:
    nginx:
      networks:
        - inception

    wordpress:
      networks:
        - inception

    mariadb:
      networks:
        - inception

  networks:
    inception:
      driver: bridge

  bridge is the default driver — a private network on your host that containers connect to. You don't need to understand the internals, just know that
  bridge networks are isolated from your host network and from other Docker networks.

  ---
  Port exposure vs port mapping

  Two different things that are easy to confuse:

  EXPOSE in Dockerfile — says "this container listens on this port." Documentation only, doesn't open anything.

  ports: in docker-compose — actually maps a host port to a container port. Makes it reachable from outside Docker.

  nginx:
    ports:
      - "443:443"    # host:container — exposed to the world

  wordpress:
    # no ports: entry — not reachable from outside
    # but nginx can still reach it on the internal network

  mariadb:
    # no ports: entry — completely internal

  This is your security model:

  Internet → port 443 → nginx → (internal network) → wordpress → mariadb

  MariaDB is never reachable from outside. WordPress is never reachable from outside. Only NGINX has a door to the world, and it decides what to let
  through.

  ---
  How NGINX talks to WordPress

  WordPress runs php-fpm — a PHP process manager that listens on port 9000. NGINX doesn't serve PHP itself; it forwards PHP requests to php-fpm and returns
  the response.

  Browser → NGINX:443 → (if .php file) → wordpress:9000 (php-fpm) → response → browser

  In your NGINX config you'll have something like:

  fastcgi_pass wordpress:9000;

  wordpress resolves to the WordPress container's IP via Docker DNS. Port 9000 is php-fpm's port inside that container. This never touches the host network
  — it's all internal.

  ---
  The project's restriction on --link and network: host

  The subject forbids --link — that's an old Docker feature for connecting containers, now replaced by networks. And network: host would make a container
  share your host's network namespace directly — no isolation at all. Both are either deprecated or defeat the purpose of the exercise.

  ---
  The full picture now:

  Host machine
  └── inception network (private)
      ├── nginx ──────── port 443 mapped to host (only public entry point)
      ├── wordpress ──── reachable by nginx via "wordpress:9000"
      └── mariadb ─────── reachable by wordpress via "mariadb:3306"

● Module 7 — docker-compose in Depth
####################################
####################################

  You've already seen the basics. This module fills in the details you'll actually need to write your project's docker-compose.yml.

  ---
  Full structure of a docker-compose.yml

  services:
    service-name:
      build:
        context: ./requirements/nginx
        dockerfile: Dockerfile
      container_name: nginx
      image: nginx                  # name for the built image
      restart: unless-stopped
      ports:
        - "443:443"
      volumes:
        - /home/gonzalo/data/nginx:/etc/nginx/certs
      networks:
        - inception
      environment:
        - SOME_VAR=value
      env_file:
        - .env
      depends_on:
        - wordpress

  networks:
    inception:
      driver: bridge

  volumes:
    db-data:

  Let's go through the parts you haven't seen yet.

  ---
  build — where to find the Dockerfile

  build:
    context: ./requirements/nginx
    dockerfile: Dockerfile

  context is the directory docker-compose uses as the build root — your COPY instructions in the Dockerfile are relative to this. dockerfile is the filename
   (default is Dockerfile so you can omit it if you use that name).

  Short form if defaults are fine:
  build: ./requirements/nginx

  ---
  depends_on — startup order

  wordpress:
    depends_on:
      - mariadb

  docker-compose starts mariadb before wordpress. But — important caveat — it only waits for the container to start, not for the service inside to be ready.
   MariaDB takes a few seconds to initialize after the container starts. WordPress might try to connect before MariaDB is ready.

  The real solution is making your WordPress startup script retry the database connection. You'll handle this when writing the entrypoint scripts.

  ---
  env_file — loading variables from a file

  env_file:
    - .env

  Loads all variables from .env into the container's environment. This is how you avoid hardcoding passwords in the compose file. The .env file lives next
  to docker-compose.yml and is ignored by git.

  ---
  environment vs env_file

  environment:
    - WORDPRESS_DB_HOST=mariadb    # hardcoded, fine for non-sensitive config
    - WORDPRESS_DB_PASS=${DB_PASS} # references a variable from .env

  You can mix both. Non-sensitive config (like hostnames) can be hardcoded. Passwords come from .env via variable substitution ${}.

  ---
  The .env file

  Sits next to docker-compose.yml, never committed to git:

  # srcs/.env
  DOMAIN_NAME=gonzalo.42.fr
  DB_NAME=wordpress
  DB_USER=wpuser
  DB_PASSWORD=somepassword
  DB_ROOT_PASSWORD=rootpassword

  Docker-compose reads this file automatically if it's in the same directory. The variables are available for substitution in docker-compose.yml with
  ${VARIABLE_NAME}.

  ---
  Key docker-compose commands

  docker-compose up -d          # build images if needed, start all containers
  docker-compose up --build -d  # force rebuild images even if they exist
  docker-compose down           # stop and remove containers (data in volumes survives)
  docker-compose down -v        # stop, remove containers AND volumes (wipes data)
  docker-compose logs -f        # follow logs from all containers
  docker-compose logs nginx     # logs from one service
  docker-compose ps             # status of all services
  docker-compose exec nginx bash  # open shell in running container
  docker-compose restart nginx  # restart one service

  down without -v is your normal workflow. down -v is for when you want a completely clean slate — useful during development when you want to test the
  initialization logic from scratch.

  ---
  Your project's compose file will look roughly like this

  services:
    mariadb:
      build: ./requirements/mariadb
      container_name: mariadb
      image: mariadb
      restart: unless-stopped
      networks:
        - inception
      volumes:
        - db-data:/var/lib/mysql
      env_file:
        - .env

    wordpress:
      build: ./requirements/wordpress
      container_name: wordpress
      image: wordpress
      restart: unless-stopped
      networks:
        - inception
      volumes:
        - wp-data:/var/www/html
      env_file:
        - .env

        - mariadb

    nginx:
      build: ./requirements/nginx
      container_name: nginx
      image: nginx
      restart: unless-stopped
      networks:
        - inception

        - wp-data:/var/www/html

● Module 8 — Environment Variables and Secrets
####################################
####################################

  You already understand .env and environment:. This module covers the full picture: how variables flow from your files into the container, and why Docker
  secrets exist.

  ---
  The flow of variables

  .env file
      ↓ (docker-compose reads it)
  docker-compose.yml substitution  →  ${DB_PASSWORD}
      ↓ (passed to container at startup)
  Container ENV
      ↓ (read by entrypoint script)
  Service config / wp-config.php / my.cnf

  Each step is a handoff. Your entrypoint script is the last step — it reads the ENV variables and writes them into whatever config format the service
  expects.

  ---
  ARG vs ENV in a Dockerfile

  Two different things that look similar:

  ARG  DB_PASSWORD        # exists only during docker build
  ENV  DB_PASSWORD=value  # exists at runtime inside the container

  ARG is for build-time only — useful if you need a value while building the image (downloading something, configuring a compile flag). Gone after build.

  ENV persists into the running container. This is what your entrypoint script reads.

  You can combine them:
  ARG  DB_PASSWORD
  ENV  DB_PASSWORD=$DB_PASSWORD

  Build-time arg gets baked into runtime env. Your project won't need this pattern much — you'll pass everything via env_file at runtime.

  ---
  The problem with ENV for passwords

  Here's the issue. If you put a password in ENV:

  ENV DB_PASSWORD=secret

  That password is baked into the image layer. Anyone who has the image can run:

  docker inspect my-mariadb

  And see all environment variables in plain text. Also visible in docker history, readable by any process inside the container, and logged by some tools.

  For a school project this is borderline acceptable. For production it's not. The subject requires Docker secrets precisely to teach you the proper way.

  ---
  Docker secrets

  A secret is a file whose contents are made available to a container at a specific path: /run/secrets/<secret_name>. The contents are never exposed as
  environment variables.

  Define secrets in docker-compose.yml:

  services:
    mariadb:
      secrets:
        - db_password
        - db_root_password

  secrets:
    db_password:
      file: ../secrets/db_password.txt
    db_root_password:
      file: ../secrets/db_root_password.txt

  The secret files (in secrets/ directory, git-ignored):
  secrets/db_password.txt      → contains: mypassword
  secrets/db_root_password.txt → contains: myrootpassword

  Inside the container, your entrypoint script reads them as files:

  DB_PASSWORD=$(cat /run/secrets/db_password)
  DB_ROOT_PASSWORD=$(cat /run/secrets/db_root_password)

  The password never touches an environment variable. It's read directly from a file that only exists inside the container's memory (it's a tmpfs mount —
  RAM, not disk).

  ---
  Your project's secrets structure

  The subject gives you the exact layout:

  secrets/
  ├── credentials.txt       # WordPress admin credentials
  ├── db_password.txt       # WordPress DB user password
  └── db_root_password.txt  # MariaDB root password

  The .env file handles non-sensitive config

  Your MariaDB entrypoint script will do something like:

  DB_PASSWORD=$(cat /run/secrets/db_password)
  DB_ROOT_PASSWORD=$(cat /run/secrets/db_root_password)

● Module 9 — PID 1 and Process Management
####################################
####################################

  Short but important. The subject explicitly mentions it and evaluators ask about it.

  ---
  What PID 1 is

  On any Linux system, the first process that starts gets PID 1. On a normal machine that's init or systemd — the process manager that starts everything
  else.

  In a container, PID 1 is whatever you put in CMD or ENTRYPOINT. If you write:

  CMD ["nginx", "-g", "daemon off;"]

  Then nginx is PID 1 inside the container.

  ---
  Why PID 1 is special

  Two reasons:

  Signal handling. When you run docker stop, Docker sends a SIGTERM to PID 1, waits 10 seconds, then sends SIGKILL. A normal process handles SIGTERM and
  shuts down gracefully. But the Linux kernel gives PID 1 special treatment — default signal handlers don't apply. If your PID 1 doesn't explicitly handle
  SIGTERM, it ignores it and gets killed hard after 10 seconds. Nginx and MariaDB handle signals correctly, so this isn't a problem for your project — but
  it's why you need to be deliberate about what runs as PID 1.

  Zombie reaping. When a child process exits, it becomes a "zombie" until its parent calls wait() to collect its exit status. On a normal system, if a
  parent dies, init (PID 1) adopts orphaned processes and reaps their zombies. In a container, if your PID 1 doesn't do this, zombies accumulate. Again, for
   single-process containers this doesn't matter — but it's why the subject warns against naive setups.

  ---
  Why the subject forbids these patterns

  # FORBIDDEN
  CMD tail -f /dev/null
  CMD sleep infinity
  CMD while true; do sleep 1; done

  These are hacks to keep a container alive without running the actual service. They tell the evaluator you don't understand what should be running as PID
  1. The real service should be PID 1 — not a placeholder.

  # FORBIDDEN
  CMD bash

  Same problem. Bash as PID 1 just sitting there doing nothing is not a service.

  ---
  The exec pattern in entrypoint scripts

  This is why every entrypoint script ends with exec:

  #!/bin/bash

  # ... setup work ...

  exec mysqld          # replaces the shell with mysqld

  Without exec:
  PID 1: bash (your script)
    └── PID 2: mysqld (child of bash)

  Shell is PID 1. Docker watches the shell. SIGTERM goes to bash, not mysqld. Bash might exit, mysqld gets killed without a chance to flush data.

  With exec:
  PID 1: mysqld (shell replaced itself)

  mysqld is PID 1. Docker talks directly to mysqld. Clean shutdown, proper signal handling.

  ---
  What this means for your three services

  ┌───────────────────┬─────────────────┬──────────────────────────────────────┐
  │      Service      │      PID 1      │                 How                  │
  ├───────────────────┼─────────────────┼──────────────────────────────────────┤
  │ NGINX             │ nginx process   │ CMD ["nginx", "-g", "daemon off;"]   │
  ├───────────────────┼─────────────────┼──────────────────────────────────────┤
  │ WordPress/php-fpm │ php-fpm process │ entrypoint ends with exec php-fpm -F │
  ├───────────────────┼─────────────────┼──────────────────────────────────────┤
  │ MariaDB           │ mysqld process  │ entrypoint ends with exec mysqld     │
  └───────────────────┴─────────────────┴──────────────────────────────────────┘

  Each one runs in the foreground, doesn't daemonize, handles signals correctly.

  ---
  The forbidden commands in context

  The subject also forbids tail -f and sleep infinity specifically because they've been used historically as workarounds to keep containers alive. If you
  find yourself reaching for them, it means the real service isn't running correctly in the foreground — fix that instead.

● PID 1 and SIGTERM

  You understood correctly, and your instinct is right too. Let me be more precise.

  Normally, every signal has a default action defined by the kernel. For SIGTERM the default action is "terminate the process." If a process doesn't install
   a custom handler, the kernel applies the default — the process dies.

  PID 1 is the exception. The kernel disables default signal actions for PID 1. If PID 1 doesn't explicitly install a handler for SIGTERM, the signal is
  silently ignored. The process doesn't die.

  Why? Historical reason: on a real system PID 1 is init/systemd. If it could be accidentally killed by a stray SIGTERM, the whole system would collapse
  with no recovery. So the kernel protects it. In a container, that protection applies to whatever happens to be PID 1 — even if it's nginx, which never
  asked for it.

  So:
  - Normal process + no SIGTERM handler → kernel default → process dies
  - PID 1 + no SIGTERM handler → kernel does nothing → process ignores it → docker waits 10s → SIGKILL → dies hard

  SIGKILL always works on everything, PID 1 included. It cannot be caught, blocked, or ignored by anyone — that's enforced by the kernel with no exceptions.

  The practical consequence for your project: nginx, php-fpm, and mysqld all install their own SIGTERM handlers, so this isn't a problem. But if you put
  bash as PID 1 and bash doesn't handle SIGTERM, docker stop hangs for 10 seconds every time.

  ---
  Why the hacks exist

  You're thinking about it from the operator's perspective — "I know I want to stop it, why keep it alive?"

  The hacks come from a different scenario: a container whose main process finishes immediately.

  Imagine you're debugging. You want a container with a specific environment to poke around in, but you don't have a long-running service to put in it yet.
  Or you're writing the entrypoint script and it crashes before you've gotten the service working. The container starts and exits in milliseconds — too fast
   to docker exec into it and inspect what's wrong.

  So people did:
  CMD sleep infinity

  Just to keep it alive long enough to get a shell in and debug.

  It became a bad habit. Some people shipped containers like this — the actual service started as a child of the sleep, or was never started at all. The
  subject forbids it because it's a sign you're not running the real service as PID 1.

  The legitimate version of "I need a container to stay alive for debugging" is docker run -it ... bash — interactive, intentional, clearly not production.
